# Карта пользовательских историй (User Story Map)

**Проект:** агрегатор и анализ рынка вакансий на основе hh.ru  
**Версия:** 1.0  
**Статус:** базовая карта текущего продукта и целевого развития

## 1. Цель продукта

Дать соискателю и аналитику единое место, где можно изучать вакансии, сравнивать требования и зарплаты, оценивать динамику спроса и находить навыки для развития. Администратор проекта должен иметь возможность получать данные из официального API hh.ru, контролировать качество и повторно запускать обработку.

Карта описывает пользовательские потребности, а не внутренние технические задачи. Архитектурные решения приведены отдельно в ТЗ и документе по архитектуре.

## 2. Персоны

| Персона | Цель | Основные вопросы |
|---|---|---|
| Соискатель / студент | Понять требования рынка и спланировать развитие навыков | Какие навыки нужны? Какие вакансии мне подходят? Какой навык изучить следующим? |
| Аналитик / исследователь | Исследовать спрос, зарплаты и географию | Какие направления востребованы? Как различаются зарплаты? Как меняется спрос? |
| Оператор данных | Поддерживать актуальность и качество набора | Когда был сбор? Сколько записей загружено? Какие ошибки возникли? |
| Преподаватель / проверяющий | Проверить воспроизводимость и обоснованность результатов | Откуда данные? Как рассчитаны показатели? Какие ограничения у прогнозов? |

## 3. Карта действий пользователя

| Этап (backbone) | Пользовательская активность | Истории (user stories) | Критерий результата |
|---|---|---|---|
| 1. Открыть систему | Перейти на сайт и понять состояние данных | Как пользователь, я хочу видеть назначение системы и дату/состояние последнего обновления, чтобы понимать актуальность информации | Главная страница открывается; статус данных не скрывает источник и ограничения |
| 2. Настроить выборку | Выбрать период, регион, направление и тип данных | Как аналитик, я хочу применять единые фильтры ко всем разделам, чтобы сравнивать показатели на одной выборке | Фильтры влияют на все аналитические страницы согласованно |
| 3. Изучить рынок | Посмотреть объём вакансий, динамику и распределения | Как пользователь, я хочу видеть ключевые показатели и динамику публикаций, чтобы быстро оценить ситуацию | KPI и графики отражают выбранную выборку; есть пояснения к формулам |
| 4. Сравнить зарплаты | Сопоставить зарплаты по роли, региону, опыту и навыкам | Как соискатель, я хочу видеть медианы и объём наблюдений, чтобы не делать выводы по малой выборке | Валюта и gross/net не смешиваются; малые группы отмечаются |
| 5. Изучить навыки | Найти востребованные технологии и совместные навыки | Как студент, я хочу видеть частоту навыков и их динамику, чтобы выбирать направления обучения | Частоты считаются по уникальным вакансиям; тренды показывают окно сравнения и объём |
| 6. Оценить географию | Сравнить регионы по числу вакансий и зарплатам | Как соискатель, я хочу сравнить регионы, чтобы оценить возможности трудоустройства | Видны вакансии, доли, зарплаты и размер выборки; неизвестная география не выдумывается |
| 7. Сопоставить себя с рынком | Указать имеющиеся навыки и увидеть подходящие вакансии | Как соискатель, я хочу оценить совпадение моих навыков с требованиями вакансий и увидеть пробелы | Процент совпадения объяснён; список недостающих навыков доступен |
| 8. Получить ориентир | Изучить прогноз и тренды | Как аналитик, я хочу видеть прогноз только при достаточной истории и проверку ошибки, чтобы оценивать надёжность результата | Прогноз сопровождается backtest, MAE и ограничениями; при недостатке истории выводится причина |
| 9. Найти вакансию | Искать и фильтровать объявления, открыть первоисточник | Как соискатель, я хочу искать по тексту, навыкам, опыту и зарплате, чтобы находить релевантные предложения | Есть карточный и табличный вид, сортировка, пагинация и ссылка на hh.ru |
| 10. Проверить качество | Посмотреть пропуски, ошибки и историю ETL | Как оператор, я хочу видеть результат каждого запуска и причины отклонений, чтобы контролировать качество | Счётчики и ошибки отражают фактический запуск |
| 11. Обновить данные | Запустить сбор из hh.ru или импорт | Как оператор, я хочу повторно получать данные без дублирования, чтобы поддерживать актуальность базы | Повторная загрузка идемпотентна; ограничения API соблюдаются |
| 12. Использовать результаты | Выгрузить таблицу для дальнейшего анализа | Как аналитик, я хочу скачать отфильтрованные данные в CSV, чтобы использовать их в отчётах | Экспорт соответствует активным фильтрам и не раскрывает лишние персональные данные |

## 4. Приоритеты (release slices)

### Релиз 1 — рабочий учебный продукт (реализованная основа)
- получение вакансий через API hh.ru и импорт файлов;
- ETL, нормализация, дедупликация, UPSERT и журнал запусков;
- хранение в SQLite/PostgreSQL;
- восемь разделов дашборда;
- глобальные фильтры, аналитика зарплат и навыков;
- каталог, CSV-выгрузка и контроль качества.

### Релиз 2 — повышение аналитической ценности
- сравнение соседних периодов;
- динамика долей навыков;
- расширенные карточки каталога;
- выгрузка региональных и зарплатных сводок;
- более ясные пояснения к прогнозу и ограничениям.

**Статус:** часть улучшений уже внесена в код и ожидает проверки на рабочем приложении.

### Релиз 3 — архитектурное развитие
- отдельный Frontend и Backend/API;
- единый контракт API и обработка ошибок;
- пользовательские сценарии без привязки к Streamlit;
- проверка адаптивности и доступности;
- автоматизированные интеграционные тесты и наблюдаемость.

**Статус:** планируется; не считать реализованным до появления отдельных приложений и API.

## 5. Ключевые пользовательские сценарии

### Сценарий A. Студент выбирает навык для изучения
1. Открывает «Навыки».
2. Смотрит рейтинг навыков в выборке.
3. Сравнивает доли за два периода, если данных достаточно.
4. Переходит в «Что выучить».
5. Отмечает уже известные навыки.
6. Изучает подходящие вакансии и навыки, которые расширят покрытие.

**Успех:** пользователь получает объяснимый список возможностей и понимает, что расчёт описывает текущую выборку, а не гарантирует трудоустройство.

### Сценарий B. Аналитик сравнивает зарплаты
1. Устанавливает период, регион и профессиональное направление.
2. Выбирает основу зарплаты (валюта и gross/net).
3. Сравнивает медианы по ролям и регионам.
4. Проверяет размер каждой группы и предупреждения о малой выборке.
5. Экспортирует сводную таблицу.

**Успех:** сравниваются только сопоставимые значения, а объём выборки виден.

### Сценарий C. Оператор обновляет данные
1. Открывает «Качество данных».
2. Проверяет настройки сбора.
3. Запускает сбор из официального API.
4. Ожидает завершения.
5. Проверяет полученные, валидные, новые, обновлённые, неизменённые и отклонённые записи.
6. При ошибке изучает сообщение и журнал.

**Успех:** запуск имеет фактический статус, повторный сбор не создаёт дубликаты.

## 6. Вне границ продукта

- автоматическое трудоустройство и отправка откликов от имени пользователя;
- гарантирование достоверности сведений работодателя;
- прогнозирование индивидуальной зарплаты как гарантированного результата;
- обход ограничений, CAPTCHA или правил API hh.ru;
- сбор персональных данных соискателей;
- представление выборки текущей базы как полного рынка труда.

## 7. Открытые вопросы для следующей версии

- Нужны ли пользовательские аккаунты и сохранённые подборки?
- Нужны ли избранные вакансии и уведомления?
- Должен ли сбор выполняться по расписанию или только вручную?
- Нужны ли дополнительные источники кроме hh.ru?
- Какой объём данных и частота обновления будут целевыми?

Эти решения не включены в текущий обязательный объём без отдельного согласования.

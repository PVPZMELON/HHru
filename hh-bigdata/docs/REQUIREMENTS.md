# Система требований к агрегатору вакансий

**Версия:** 1.0  
**Основание:** текущая реализация репозитория и карта пользовательских историй `USER_STORY_MAP.md`.

## 1. Назначение и границы

Система собирает вакансии из официального API hh.ru и файловых источников, нормализует и сохраняет их в реляционной БД, рассчитывает аналитические показатели и предоставляет веб-интерфейс для исследования рынка труда.

Основной пользовательский интерфейс текущей версии реализован на Streamlit. Разделение на независимые Frontend и Backend/API является целевым этапом развития, а не описанием текущей архитектуры.

## 2. Термины

| Термин | Определение |
|---|---|
| Вакансия | Объявление о работе, полученное из источника |
| ETL | Extract — получение, Transform — преобразование, Load — загрузка |
| UPSERT | Вставка новой записи или обновление существующей |
| Идемпотентность | Повторная обработка тех же данных не создаёт повторных записей |
| Gross / net | Зарплата до / после налогов согласно признаку источника |
| Сопоставимая зарплата | Вилка «от–до» с одной валютой и известным gross/net |
| Синтетические данные | Демонстрационные записи, созданные генератором, а не полученные с рынка |
| Backtest | Проверка модели на отложенном историческом участке |

## 3. Функциональные требования

Приоритеты: **MUST** — обязательно; **SHOULD** — желательно; **COULD** — опционально.

| ID | Приоритет | Требование | Критерий приёмки |
|---|---|---|---|
| FR-01 | MUST | Система должна получать вакансии через официальный API hh.ru по поисковым запросам и регионам | В журнале фиксируются параметры и счётчики запуска |
| FR-02 | MUST | Сборщик должен соблюдать лимиты, паузы, таймауты и допустимые повторы | Нет обхода 401/403/CAPTCHA; ошибки отражаются в статусе |
| FR-03 | MUST | Система должна поддерживать импорт JSONL, JSON и CSV | Валидный файл загружается; некорректные строки учитываются в отчёте |
| FR-04 | MUST | Сырые ответы должны сохраняться отдельно от нормализованных данных, если включено сохранение raw | Raw-файл не заменяет записи БД; путь фиксируется при доступности |
| FR-05 | MUST | Каждая вакансия должна проходить нормализацию и валидацию | Отсутствие ID или названия приводит к отклонению с причиной |
| FR-06 | MUST | Система должна нормализовать даты, текст, зарплату и навыки | Правила едины и описаны в METRICS.md/архитектуре |
| FR-07 | MUST | Система должна удалять точные дубли и идемпотентно обновлять записи | Повторный запуск не увеличивает число записей без новых ID |
| FR-08 | MUST | Данные должны храниться в SQLite или PostgreSQL | Миграции применяются повторно без разрушения данных |
| FR-09 | MUST | Система должна журналировать каждый ETL-запуск | Доступны статус, время, параметры и счётчики |
| FR-10 | MUST | Система должна фиксировать проблемы качества | Есть тип проблемы и связь с запуском/записью, где применимо |
| FR-11 | MUST | Веб-интерфейс должен предоставлять глобальные фильтры | Фильтры согласованно влияют на аналитические страницы |
| FR-12 | MUST | Обзор должен показывать KPI и динамику публикаций | Для каждого показателя есть определение и единица |
| FR-13 | MUST | Аналитика зарплат должна соблюдать сопоставимость валюты и gross/net | Несопоставимые значения не смешиваются |
| FR-14 | MUST | Аналитика навыков должна считать частоту по уникальным вакансиям | Один навык не увеличивает счётчик многократно в одной вакансии |
| FR-15 | MUST | Каталог должен поддерживать поиск, фильтры, сортировку и пагинацию | Запросы выполняются для текущей выборки; пустой результат объясняется |
| FR-16 | MUST | Каталог должен давать ссылку на оригинал вакансии, если она есть | Ссылка открывает исходное объявление |
| FR-17 | MUST | Система должна поддерживать CSV-экспорт аналитических таблиц и каталога | Файл соответствует выбранным фильтрам и имеет понятные заголовки |
| FR-18 | MUST | Раздел «Качество данных» должен показывать фактические ETL-запуски и пропуски | Нельзя показывать выдуманный статус или подменять пустую историю |
| FR-19 | SHOULD | Система должна показывать тренды спроса на навыки по двум временным окнам | Периоды и минимальный объём наблюдений явно указаны |
| FR-20 | SHOULD | Система должна строить прогноз потока публикаций при достаточной истории | Показываются backtest, MAE, сравнение с наивной моделью и ограничения |
| FR-21 | SHOULD | Система должна сопоставлять навыки пользователя с требованиями вакансий | Показаны правила покрытия, подходящие вакансии и пробелы |
| FR-22 | SHOULD | Каталог должен иметь карточный и табличный режим | В обоих режимах доступны ключевые поля и ссылка |
| FR-23 | SHOULD | Система должна сравнивать соседние временные периоды | Формула изменения и границы периодов указаны |
| FR-24 | COULD | В целевой архитектуре интерфейс должен быть отделён от серверной логики | Отдельный frontend обращается к backend через документированный API |
| FR-25 | COULD | В целевой архитектуре должны быть предусмотрены роли пользователей | Доступ ограничивается по ролям после согласования модели доступа |

## 4. Бизнес-правила и ограничения данных

### BR-01. Происхождение данных
Каждая запись должна сохранять происхождение: API, импорт или синтетический набор. Синтетические записи должны быть явно помечены и не должны выдаваться за реальные вакансии.

### BR-02. Идентификация
Основной ключ источника — сочетание источника и идентификатора вакансии. Отсутствие обязательного ID или названия приводит к отклонению записи с регистрацией причины.

### BR-03. Дедупликация
Повторная запись с тем же ID и тем же содержимым не создаёт новую вакансию. Изменившееся содержимое обрабатывается как обновление по правилам ETL.

### BR-04. Зарплата
Для сопоставления используются только корректные вилки «от–до» с одной валютой и известным признаком gross/net. Валюты не конвертируются без отдельного проверенного курса. Односторонние значения хранятся, но не смешиваются с вилками.

### BR-05. Минимальная группа
Группы с количеством сопоставимых зарплат ниже заданного порога не должны интерпретироваться как надёжное сравнение. В интерфейсе указывается n и статус достаточности.

### BR-06. Аналитические выводы
Наблюдаемая связь между навыком и зарплатой не должна называться причинным влиянием. Прогноз не должен показываться как гарантия будущего значения.

### BR-07. Актуальность
Текущая БД содержит актуальные объявления и не обязательно представляет полный архив рынка за каждый день. Сравнение публикаций и тренды должны сопровождаться предупреждением о возможном смещении выборки.

### BR-08. Внешний источник
Система не должна обходить ограничения API hh.ru, CAPTCHA, авторизацию или правила использования источника.

## 5. Нефункциональные требования

| ID | Категория | Требование |
|---|---|---|
| NFR-01 | Безопасность | Токены и пароли хранятся в секретах окружения/платформы, не в репозитории и не в логах |
| NFR-02 | Безопасность | SQL-запросы должны быть параметризованными |
| NFR-03 | Надёжность | Ошибка ETL не должна оставлять частично записанную транзакцию |
| NFR-04 | Надёжность | Повторное применение миграций не должно повреждать схему |
| NFR-05 | Производительность | Каталог должен использовать серверную пагинацию, а не загружать весь набор для каждой страницы |
| NFR-06 | Производительность | Повторные запросы справочников и аналитики могут кэшироваться с явным механизмом сброса |
| NFR-07 | Удобство | Интерфейс должен быть русскоязычным, адаптивным и единообразным |
| NFR-08 | Доступность | Цвет не должен быть единственным способом передачи статуса; текстовые подписи обязательны |
| NFR-09 | Сопровождаемость | ETL, БД, аналитика и интерфейс должны оставаться логически разделёнными |
| NFR-10 | Проверяемость | Ключевые правила ETL, метрик, фильтров и прогнозов покрываются автоматическими тестами |
| NFR-11 | Переносимость | Конфигурация должна задаваться через переменные окружения/секреты |
| NFR-12 | Прозрачность | Источник, дата сбора, размер выборки, методика и ограничения показателей должны быть доступны пользователю |

## 6. Матрица трассируемости

| История | Требования |
|---|---|
| Изучить рынок | FR-11, FR-12, BR-07 |
| Сравнить зарплаты | FR-13, BR-04, BR-05 |
| Изучить навыки | FR-14, FR-19, BR-06 |
| Оценить географию | FR-11, FR-17 |
| Сопоставить себя с рынком | FR-21, BR-06 |
| Получить прогноз | FR-20, BR-07 |
| Найти вакансию | FR-15, FR-16, FR-22 |
| Проверить качество | FR-09, FR-10, FR-18 |
| Обновить данные | FR-01—FR-08, BR-01—BR-03, BR-08 |

## 7. Условия приёмки проекта

Проект можно считать готовым к демонстрации, если:
1. Миграции создают рабочую схему БД.
2. Реальный или тестовый источник проходит через ETL с регистрацией результата.
3. Повторная загрузка не создаёт дубликатов.
4. Все страницы используют фактические данные БД.
5. Зарплатные сравнения соблюдают правила сопоставимости.
6. Ошибки и пропуски видны пользователю.
7. Прогноз и тренды не скрывают недостаток данных.
8. Сбор и выгрузка не раскрывают секреты.
9. Основные сценарии проверены тестами и на развернутом приложении.

Подробный сценарий тестирования приведён в техническом задании.

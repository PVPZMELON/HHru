# Техническое задание
## Агрегатор и анализ рынка вакансий на основе данных hh.ru

**Версия:** 1.0  
**Статус:** проект ТЗ для учебной разработки  
**Основание:** `USER_STORY_MAP.md`, `REQUIREMENTS.md`, текущий код репозитория.

## 1. Общие сведения

### 1.1. Наименование
«Агрегатор и анализ рынка вакансий на основе данных hh.ru с использованием технологий Big Data».

### 1.2. Заказчик и исполнитель
Учебный проект. Заказчик — преподаватель дисциплины «Большие данные». Исполнитель — студент-разработчик.

### 1.3. Назначение
Разработка веб-приложения для сбора, обработки, хранения и анализа вакансий. Система предназначена для изучения рынка труда, требований к специалистам, зарплатных диапазонов и регионального распределения.

### 1.4. Основание для разработки
Задание по дисциплине «Большие данные» и требования к учебному проекту, сформированные в ходе анализа пользовательских сценариев.

## 2. Цели и задачи

Цели:
- создать воспроизводимый конвейер получения и обработки вакансий;
- обеспечить централизованное хранение и контроль качества;
- реализовать интерактивную аналитику рынка;
- дать соискателю инструменты изучения востребованных навыков;
- подготовить основу для последующего разделения Frontend и Backend.

Задачи:
1. Получение данных через официальный API hh.ru и файловый импорт.
2. Сохранение исходных данных и нормализация полей.
3. Дедупликация и идемпотентная загрузка в БД.
4. Расчёт аналитических метрик.
5. Разработка интерфейса с фильтрами и визуализациями.
6. Контроль качества, журналирование и обработка ошибок.
7. Подготовка документации, тестов и инструкции развёртывания.

## 3. Пользователи и роли

| Роль | Возможности |
|---|---|
| Посетитель / соискатель | Просмотр аналитики, поиск вакансий, анализ навыков и зарплат |
| Аналитик | Фильтрация, сравнение, изучение трендов, CSV-экспорт |
| Оператор | Запуск сбора, проверка ETL-истории и ошибок |
| Администратор | Настройка секретов и инфраструктуры развёртывания |

В текущей версии отдельная система регистрации и разграничения ролей не заявляется. Это ограничение должно быть учтено при переводе интерфейса в отдельный frontend.

## 4. Функциональный состав

### 4.1. Сбор данных
- Источник: официальный API hh.ru.
- Параметры: поисковые запросы, регионы, лимит, пагинация, получение подробностей, задержка.
- Авторизация: секрет окружения; токен не хранится в исходном коде.
- Ограничения: соблюдать лимиты источника; не обходить CAPTCHA, 401/403 и другие ограничения.
- Альтернативный путь: импорт JSONL, JSON и CSV.
- Для каждого запуска сохранять параметры, время, статус и счётчики.

### 4.2. Обработка данных
- Проверка обязательных полей.
- Очистка текстовых полей.
- Приведение дат к единому формату/UTC.
- Нормализация зарплат и валютных признаков.
- Извлечение структурированных навыков и словарных упоминаний.
- Дедупликация по идентификатору источника.
- Регистрация ошибок и пропусков.

### 4.3. Хранение
Основная СУБД развернутого приложения — PostgreSQL. Для локальной разработки и демонстрации допускается SQLite. Управление схемой — SQL-миграциями. Повторная загрузка должна быть идемпотентной.

Основные сущности: вакансии, работодатели, регионы, профессиональные роли, навыки, связи вакансий и навыков, ETL-запуски, проблемы качества.

### 4.4. Аналитика
Система должна отображать:
- количество вакансий и работодателей;
- долю вакансий с указанной зарплатой;
- медиану, среднее и квартили сопоставимых зарплат;
- распределение по регионам, ролям, опыту и занятости;
- динамику публикаций;
- востребованность навыков и совместную встречаемость;
- сравнение зарплат по группам и навыкам;
- оценку соответствия навыков пользователя требованиям;
- прогноз публикаций при достаточной истории и оценку качества прогноза.

Формулы и правила приведены в `METRICS.md`.

### 4.5. Пользовательский интерфейс
Текущая версия содержит восемь разделов:
1. Обзор.
2. Зарплаты.
3. Навыки.
4. География.
5. Что выучить.
6. Прогноз.
7. Каталог вакансий.
8. Качество данных.

Общие элементы: боковая панель фильтров, единая визуальная тема, графики, таблицы, пояснения к показателям и CSV-экспорт там, где он предусмотрен.

### 4.6. Качество данных
Пользователь должен иметь возможность увидеть:
- историю ETL-запусков;
- источник и параметры запуска;
- полученные, валидные, новые, обновлённые, неизменённые, дублированные и отклонённые записи;
- проблемы и пропуски;
- статус последнего запуска.

## 5. Требования к интерфейсу и UX

- Язык интерфейса — русский.
- Основная палитра: светлый фон, графитовый текст, лаймовый акцент.
- Сетка: крупный вводный блок, KPI-карточки, аналитические панели и таблицы.
- Карточки и элементы управления должны иметь единый радиус, отступы и состояния.
- Цвета графиков должны быть согласованы с темой и иметь достаточный контраст.
- На мобильных экранах блоки должны перестраиваться в одну колонку.
- Пустые состояния должны объяснять, почему данных нет и что можно сделать.
- Любая статистика должна иметь подпись о методике и размере выборки.
- Не использовать визуальные эффекты, мешающие чтению данных.

## 6. Требования к данным и методике

1. Не смешивать синтетические и реальные данные без явной маркировки.
2. Не смешивать валюты и gross/net в сравнении зарплат.
3. Не считать одностороннюю зарплату «от» или «до» полноценной вилкой.
4. Указывать размер выборки для медиан и групповых сравнений.
5. Не трактовать корреляции и ассоциации как причинно-следственные связи.
6. Не показывать прогноз при недостаточной истории.
7. Указывать ошибку backtest и сравнение с простой базовой моделью.
8. Указывать, что база актуальных вакансий может не быть полным историческим архивом.

## 7. Архитектура и технологии

### 7.1. Текущая архитектура
- Python — ETL, конфигурация и аналитические функции.
- requests — HTTP-клиент API.
- Pandas/NumPy — преобразование и аналитика.
- SQLAlchemy — доступ к БД.
- PostgreSQL / SQLite — хранение.
- Streamlit — пользовательский интерфейс.
- Plotly — графики.
- Pydantic — настройки.
- pytest — тестирование.
- Streamlit Community Cloud — размещение интерфейса; PostgreSQL размещается отдельно.

### 7.2. Целевая архитектура развития
Отдельные приложения:
- `frontend/` — пользовательский интерфейс и клиент API;
- `backend/` — серверное API, бизнес-логика и аналитические сервисы;
- `migrations/` — версия схемы БД;
- PostgreSQL — постоянное хранилище.

Предлагаемый вариант: React + TypeScript для frontend; FastAPI для backend; PostgreSQL для БД. Это целевая рекомендация, а не уже реализованный стек. Перед миграцией необходимо утвердить API-контракт и сохранить рабочую Streamlit-версию как контрольный прототип.

## 8. Требования к API целевой версии

Предлагаемые ресурсы API (контракт подлежит уточнению при реализации):

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/overview` | KPI и сводная аналитика |
| GET | `/api/v1/vacancies` | Поиск и пагинация вакансий |
| GET | `/api/v1/vacancies/{id}` | Подробности вакансии |
| GET | `/api/v1/analytics/salaries` | Зарплатная аналитика |
| GET | `/api/v1/analytics/skills` | Востребованность и тренды навыков |
| GET | `/api/v1/analytics/regions` | Региональная аналитика |
| GET | `/api/v1/analytics/forecast` | Прогноз и оценка ошибки |
| GET | `/api/v1/etl/runs` | История ETL |
| POST | `/api/v1/etl/collect` | Запуск сбора при наличии прав оператора |
| GET | `/api/v1/health` | Состояние сервиса |

Формат обмена — JSON. Для списков предусмотреть `items`, `total`, `page`, `page_size`. Ошибки должны иметь стабильный код и безопасное сообщение. Секреты, токены и полные тексты ошибок инфраструктуры клиенту не возвращаются.

## 9. Требования к безопасности

- Секреты хранятся в Secrets/переменных окружения.
- Запрещено коммитить токены, пароли и реальные выгрузки с чувствительными данными.
- Логи не должны содержать секреты.
- SQL — параметризованный.
- Внешние URL в каталоге должны относиться к ожидаемому источнику; открытие ссылки — по явному действию пользователя.
- При появлении авторизации операции сбора должны быть защищены ролью оператора.
- Не обходить технические и юридические ограничения источника.

## 10. Развёртывание и эксплуатация

Текущая схема:
- код приложения — GitHub;
- Streamlit — Streamlit Community Cloud;
- БД — PostgreSQL (Neon);
- параметры подключения и токен API — Secrets приложения.

Целевая схема:
- frontend и backend публикуются отдельно или через единый reverse proxy;
- PostgreSQL остаётся отдельным управляемым сервисом;
- миграции запускаются контролируемо до запуска новой версии;
- health-check подтверждает доступность backend и БД;
- резервное копирование выполняется средствами провайдера БД.

## 11. Проверка и приёмка

| № | Проверка | Ожидаемый результат |
|---|---|---|
| 1 | Открытие главной страницы | KPI и данные отображаются либо объясняется пустое состояние |
| 2 | Изменение глобальных фильтров | Все страницы используют ту же выборку |
| 3 | Сбор вакансий | ETL-запуск отражён в журнале |
| 4 | Повторный сбор тех же вакансий | Дубликаты не создаются |
| 5 | Ошибка API / недоступность БД | Ошибка показана безопасно, статус запуска корректен |
| 6 | Зарплатное сравнение | Валюта и gross/net не смешиваются |
| 7 | Маленькая группа зарплат | Группа помечена как недостаточная |
| 8 | Прогноз при короткой истории | Прогноз не строится, отображается причина |
| 9 | Каталог | Поиск, сортировка, пагинация и ссылки работают |
| 10 | CSV | Файл соответствует выбранным фильтрам |
| 11 | Адаптивность | Интерфейс читаем на узком экране |
| 12 | Секреты | Токен и пароль отсутствуют в коде и логах |

## 13. Допущения и ограничения

- Данные зависят от доступности и правил API hh.ru.
- Набор вакансий не гарантирует полноту рынка.
- Прогноз имеет исследовательский характер.
- Наличие координат и геометрий регионов не предполагается без отдельного источника.
- Целевая архитектура Frontend/Backend требует отдельной реализации и не считается выполненной текущим Streamlit-приложением.
